# Licensing

> Not legal advice. This records engineering policy chosen to keep commercial options open.
> Actual licensing or sale agreements need qualified counsel.

## Why this document exists before any code

The repository owner may want to license, sell, or otherwise commercialise this codebase
later — including licensing it as a corpus. That is only possible if **every line is either
originally authored here or carried under a permissive licence**. Those conditions are cheap
to maintain from the start and expensive-to-impossible to retrofit, because retrofitting
means auditing and rewriting history.

## The rule: ideas are free, expression is not

Copyright protects the expression of a program — its source text, and to a degree its
structure, naming, and organisation. It does not protect concepts, architectures, algorithms,
or how a feature ought to behave.

| Activity | Result |
|---|---|
| Read a project, learn *"the approval gate should fail closed and long-poll a local server"*, then implement it here | Clean. Fully ours. |
| Copy source text, an interface definition, or a script from a non-permissive project | Carries that project's licence. Cannot be relicensed. |
| Reimplement a module with the reference open beside you, keeping its structure and naming | Grey zone. "Substantially similar" can still infringe. **Avoid.** |

## Clean-room method

For any component whose design was informed by a non-permissive project:

1. Write the behaviour into `docs/` as a functional specification — *what* it does, not *how*
   the reference does it. No code, no file layout, no naming, no comment flow.
2. Implement from that specification, with the reference repository **closed**.
3. Record it in [PRIOR-ART.md](PRIOR-ART.md): project, licence, what was learned, and
   explicitly whether any code was used.

This applies to the approval gate, scheduler, session lifecycle, settings system, and audit
feed — all informed by OpenTrade-Agent (Elastic Licence 2.0).

## Dependency policy

**Permitted:** MIT · Apache-2.0 · BSD-2-Clause · BSD-3-Clause · ISC · Zlib · Unlicense ·
CC0.

**Banned anywhere in the tree:** GPL (any version) · AGPL · LGPL · Elastic Licence · Business
Source Licence · CC-BY-SA · Server Side Public Licence · anything with a non-commercial or
field-of-use restriction.

A single copyleft dependency forecloses commercial licensing of the whole work. `cargo-deny`
enforces this from S0; the frontend is checked with `osv-scanner` and a licence checker.
Adding a dependency requires stating its licence in the PR.

## Copyright ownership

- The repository owner holds copyright in all original code here.
- Output generated by an AI assistant at the owner's direction is the owner's; Anthropic
  claims no copyright in model output.
- **If the repository accepts outside contributions, a CLA is required** — otherwise each
  contributor co-owns their contribution and the work can no longer be relicensed
  unilaterally. See [`../CONTRIBUTING.md`](../CONTRIBUTING.md).

## Current licence, and the open question

The repository currently carries **MIT**. That is the right default for a scaffold, but it is
worth naming that MIT is *permissive to the point of giving away the commercial position* —
anyone may take the code, build a product, and owe nothing.

If licence revenue is a real goal, the options are:

| Option | Shape | Trade-off |
|---|---|---|
| **MIT** (current) | Anyone may do anything | Maximum adoption, zero leverage |
| **Dual licence** | AGPL-3.0 publicly, plus a paid commercial licence | Copyleft deters commercial free-riding; you grant exceptions as the copyright holder |
| **BSL 1.1** | Source-available; commercial use needs a licence; converts to open after N years | The MariaDB / Sentry model. Source-available, not open source |
| **Proprietary** | Not published, licensed per deal | Maximum control, no community |

**No decision is made here.** Changing the licence later is straightforward *while the owner
holds all copyright* — which is exactly why the CLA and dependency policy matter now. Revisit
before v0.1 release; record the outcome as an ADR.

## What due diligence will look for

Any acquirer or corpus licensee runs provenance analysis — code fingerprinting, commit
forensics, dependency SBOM. The artifacts that survive that review:

- A clean-room trail in `PRIOR-ART.md`.
- An SBOM per release, with no non-permissive entries.
- Commit history showing implementation from specification.
- A CLA covering every contributor.

Attempting to obscure the origin of borrowed code is the worst possible finding in that
review — it reads as wilful and can end a deal. The clean path is also the commercially safe
one.
